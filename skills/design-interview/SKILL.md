# Design interview

Help the user steer an artifact toward their desired result. This initial guide follows the requested conversational approach; it does not incorporate the user's separate interview guide, which has not been supplied. If that guide arrives, read it before adapting the method and distinguish its guidance from these initial choices.

## Find the next useful question

Read the current request, prior answers, accepted choices, and existing project notes first. During iteration, inspect the actual candidate and relevant references. Carry forward settled answers; revisit them only when new feedback creates a real conflict.

Early in work with a shared artifact, establish separately what it represents and what the user wants it to become. An input may be an actual product capture, existing concept/mockup, editorial composite, or style inspiration, with multiple roles. The target may be a faithful recreation, concept mockup, editorial presentation, or something else. A screenshot input does not imply a literal screenshot output; appearance and filenames establish neither authenticity nor intent. If either role is unclear, ask a brief question about the missing part, for example: “Is this an actual product screen, an existing mockup, or a visual reference—and should we preserve it faithfully or develop it into a concept?” Adapt the wording and skip parts already settled. Clarify what must remain faithful and what may change only as needed for the next build.

Ask one focused, high-value question at a time. Use a small related batch only when answering together is easier. Explore only topics that affect the next decision: message, audience and use; liked or disliked reference qualities; practical constraints; what must remain; or what would make the current candidate closer. Do not administer these as a checklist.

Translate subjective feedback through something visible. For “too busy,” point to a specific region or compare alternatives with different amounts of context. Offer an interpretation as a hypothesis, not the user's preference. Accept written or spoken feedback in the same way. Human Review may collect localized comments when useful and available; feed those comments into the same decisions without making browser review a dependency.

## Turn answers into action

Keep a short working brief in the conversation and, when maintaining a project, its existing notes. Record **source representation**, **target representation**, and relevant **fidelity boundaries** separately, alongside consequential constraints, accepted choices and references, and the next experiment. Distinguish **user preferences**, **model hypotheses**, and **unresolved points**. Update the brief across turns instead of asking settled questions again; a missing answer is not agreement.

Stop interviewing once enough is known to build the next useful experiment. State the concrete decision and expected visible effect, then proceed within the task's authorization. Use reasonable, disclosed assumptions for nonessential gaps; ask about a missing input only when it changes what can usefully be built.

## Learn from the output

Review the actual artifact with the user's feedback. Preserve the strongest or approved version and test one consequential change while carrying forward what should stay. Record the resulting choice and its reason; reopen only the uncertainty that matters next. A model recommendation is not user approval.

Keep taste specific to the artifact and context. Do not promote it into universal design rules or write stored personal memory. Follow the selected project's identity, source ownership, and review requirements without introducing a default style or tool.
